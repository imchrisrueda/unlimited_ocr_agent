## Notes

### Contexto técnico y diseño del worker OCR en subproceso

En `mejoras.md`, el hardware objetivo cuenta con 12 GB de VRAM (NVIDIA RTX 4070 Ti 12 GB). Para evitar problemas de saturación de memoria GPU (CUDA OOM), el procesamiento se organiza en fases estrictamente secuenciales:
1. Rasterizado de páginas a imágenes (`pages/page_001.png`, etc.).
2. Inferencia OCR mediante `Unlimited-OCR` en subproceso hijo dedicado.
3. Persistencia de artefactos (`result.md`, `raw/document.md`, `raw/page_*.md`, `ipc/worker_response_<id>.json`).
4. Terminación completa del subproceso worker, forzando la liberación de memoria CUDA por parte del sistema operativo al morir el proceso.
5. Invocación de LM Studio / Qwen 3.5 9B en el proceso padre con los recursos de la GPU despejados.

### Protocolo IPC determinista y correlación por `request_id`
Para evitar respuestas obsoletas o colisiones entre invocaciones, el canal de comunicación dentro del subdirectorio temporal del run (`output_dir`) utiliza identificadores únicos:
- **Directorio IPC**: `<output_dir>/ipc/`.
- **Petición (`ipc/worker_request_<id>.json`)**:
  ```json
  {
    "version": 1,
    "request_id": "a1b2c3d4...",
    "mode": "pdf",
    "model_name": "baidu/Unlimited-OCR",
    "image_paths": ["C:/ruta/externa/o/interna/page_001.png"],
    "output_dir": "C:/runs/run_123",
    "source_result_path": null
  }
  ```
- **Respuesta atómica sin `raw_text` (`ipc/worker_response_<id>.json`)**:
  El worker escribe primero en un archivo temporal (`ipc/worker_response_<id>.json.tmp`) y efectúa un reemplazo atómico mediante `os.replace`. No transporta `raw_text` en el JSON para no duplicar cadenas grandes en memoria:
  ```json
  {
    "version": 1,
    "request_id": "a1b2c3d4...",
    "status": "success",
    "result_path": "C:/runs/run_123/result.md",
    "mapping_status": "mapped",
    "mapping_error": null,
    "page_artifacts": [
      {
        "page_number": 1,
        "image_path": "C:/runs/run_123/pages/page_001.png",
        "raw_path": "C:/runs/run_123/raw/page_001.md",
        "ocr_mapping_status": "mapped",
        "mapping_error": null
      }
    ],
    "error_type": null,
    "error_message": null,
    "traceback": null
  }
  ```
- **Lectura por el proceso padre**:
  El padre valida que `request_id` coincida con la petición, descarta/elimina respuestas obsoletas, valida que todas las rutas devueltas para escritura/resultados estén confinadas dentro de `output_dir` y lee el contenido textual directamente desde `result.md` (o `raw/document.md`).
- **Logs persistentes de diagnóstico**:
  Los flujos estándar del proceso hijo se capturan en:
  - `<output_dir>/ipc/worker_<id>_stdout.log`
  - `<output_dir>/ipc/worker_<id>_stderr.log`

### Ejecución segura del subproceso y timeout con kill/wait
- Se ejecuta mediante `subprocess` con lista de argumentos:
  `[sys.executable, "-m", "src.fieldnotes.ocr.worker", "--request", str(request_file), "--response", str(response_file)]`
- `shell=False` obligatorio en todas las plataformas.
- `timeout` configurable mediante `config.get_ocr_worker_timeout()` (variable de entorno `OCR_WORKER_TIMEOUT`, entero positivo con valor por defecto de 1800 s para dar margen a la descarga inicial de pesos del modelo).
- Ante timeout, el proceso padre ejecuta `kill()` y `wait()` sobre el proceso hijo para garantizar que no queden procesos huérfanos consumiendo GPU.

### Jerarquía de errores tipados
- `OCRError`: Excepción base del subsistema OCR.
- `OCRWorkerError(OCRError)`: Error base del worker.
- `OCRWorkerTimeoutError(OCRWorkerError)`: El worker superó el tiempo límite establecido (almacena `timeout_seconds`, `stdout_path`, `stderr_path`).
- `OCRWorkerExecutionError(OCRWorkerError)`: El worker finalizó con código de retorno != 0 (almacena `returncode`, `stdout_path`, `stderr_path`, `error_message`).
- `OCRWorkerProtocolError(OCRWorkerError)`: El archivo de respuesta no existe, no coincide el `request_id`, o contiene JSON corrupto/inválido.

### Modos de ejecución (`ocr_mode`)
- **Modo `ocr_mode='worker'` (por defecto en constructor y CLI)**:
  - El proceso principal no importa `torch` ni `transformers`.
  - Las propiedades `agent.model`, `agent.tokenizer`, `agent.device` y `agent.dtype` lanzan un `RuntimeError` informativo indicando que el modelo reside en un subproceso aislado para liberar VRAM y sugiriendo el uso de `ocr_mode='in_process'` si se precisa manipular el modelo directamente en Python.
- **Modo `ocr_mode='in_process'` (optativo)**:
  - Carga `UnlimitedOCR` directamente en el proceso padre, preservando la delegación de lectura/escritura sobre `agent.model`, `agent.tokenizer`, etc., garantizando compatibilidad retrospectiva total.

### Criterios de liberación y validación
- **Criterio primario**: El subproceso finaliza con código 0 y su PID ya no existe en la tabla de procesos del SO, sin procesos hijos remanentes.
- **Criterio secundario**: Medición de VRAM total antes y después de la ejecución del worker; la VRAM debe retornar a la línea base previa con una tolerancia amplia documentada (máx. 256 MiB o 5%) debido al comportamiento de caché de controladores WDDM y procesos concurrentes del sistema operativo (sin prometer 100% de liberación ni GPU completamente despejada).
- **Prueba de integración real (`RUN_OCR_WORKER_INTEGRATION=1`)**:
  - Ejecutada en un proceso padre limpio.
  - Verifica que `torch`/`transformers` no aparecieron en `sys.modules` del padre como resultado de la ejecución del worker.
  - Verifica la terminación del subproceso y el retorno de VRAM dentro de la tolerancia.
