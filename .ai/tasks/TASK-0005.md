## Resumen Ejecutivo

TASK-0005 (correspondiente a **PR 5** de `mejoras.md`) introduce los esquemas tipados con Pydantic v2 (`pydantic>=2.12.0,<3.0.0`) y el motor de **structured outputs** como la frontera tipada entre las respuestas multimodales de LM Studio (implementadas en PR 4) y la lógica de dominio.

El objetivo fundamental es capturar objetos estructurados rigurosamente validados que preserven la evidencia (separando el texto crudo leído de su normalización), la página de procedencia y la incertidumbre, evitando que el VLM emita Markdown no estructurado para tareas con estructura conocida (como tablas de notas de campo/estadillos).

---

## Decisiones de Diseño y Arquitectura

### 1. Jerarquía de Módulos sin Ciclos de Importación (`src/fieldnotes/vlm/errors.py`)

Para eliminar cualquier posibilidad de importación circular entre el cliente LM Studio y los helpers estructurados:
- **`src/fieldnotes/vlm/errors.py`**: Módulo neutral que aloja la jerarquía unificada de excepciones:
  - `LMStudioError` (base)
  - `LMStudioConnectionError`
  - `LMStudioModelNotConfiguredError`
  - `LMStudioModelNotFoundError`
  - `LMStudioResponseError`
  - `LMStudioEmptyResponseError`
  - `StructuredOutputError` (derivada de `LMStudioError`)
  - `StructuredOutputParseError` (error de sintaxis JSON o bloque malformado)
  - `StructuredOutputValidationError` (fallo de validación de esquema Pydantic)
- **Flujo de importaciones**:
  - `errors.py` $\leftarrow$ `structured.py` (usa excepciones de structured outputs)
  - `errors.py` y `structured.py` $\leftarrow$ `lmstudio.py` (usa excepciones y helpers estructurados)
  - `lmstudio.py` re-exporta todas las excepciones para preservar compatibilidad con código existente.

```
                  ┌──────────────────────┐
                  │   vlm/errors.py      │
                  └──────────┬───────────┘
                             │
               ┌─────────────┴─────────────┐
               ▼                           ▼
    ┌──────────────────────┐    ┌──────────────────────┐
    │  vlm/structured.py   │◄───┤   vlm/lmstudio.py    │
    └──────────────────────┘    └──────────────────────┘
```

### 2. Compatibilidad Estricta con Python 3.11

El entorno de ejecución del proyecto es Python 3.11. Queda expresamente prohibido el uso de sintaxis PEP 695 introducida en Python 3.12 (ej. `def ask_structured[T: BaseModel]`). Se utiliza la parametrización estándar con `TypeVar` y `Generic`:

```python
from typing import TypeVar, Type, Generic
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

def ask_vision_structured(
    self,
    image_path: str | Path,
    prompt: str,
    schema: Type[T],
    ocr_context: Optional[str] = None,
    **kwargs: Any,
) -> T: ...
```

### 3. Modelo Coherente de Preservación de Evidencia (`evidence.py`)

Para evitar duplicidad confusa entre campos planos y campos de evidencia, los datos del dominio que provienen de lectura visual o que son susceptibles de interpretación/normalización se modelan mediante el contenedor genérico `EvidenceValue[T]`:

```python
class EvidenceValue(BaseModel, Generic[T]):
    raw: Optional[str] = None
    normalized: Optional[T] = None
    source_page: int = Field(..., ge=1)
    uncertain: bool = False
    alternatives: list[str] = Field(default_factory=list)

    model_config = ConfigDict(extra="forbid")
```

- En `EstadilloRow`:
  - `id: Optional[str] = None`
  - `col: Optional[int] = None`
  - `fil: Optional[int] = None`
  - `especie: EvidenceValue[str]` (contiene el texto original en `raw` y la especie en `normalized`)
  - `altura_cm: Optional[EvidenceValue[float]] = None`
  - `foto: Optional[str] = None`
  - `bbch: Optional[EvidenceValue[str]] = None`
  - `observaciones: Optional[str] = None`
  - `source_page: int = Field(..., ge=1)`
- **Invariante**: Queda prohibida la normalización silenciosa o automática en validadores de PR 5; la separación de `raw` vs `normalized` se mantiene como contrato de datos transparente.

### 4. Política Estricta vs Flexible en Esquemas

- **Esquemas de Dominio**: Todos los modelos configuran `model_config = ConfigDict(extra="forbid")` para rechazar campos no reconocidos y prevenir alucinaciones de estructura por parte del modelo.
- **Campos Flexibles**: En campos de metadatos o contexto libre (`DocumentIR.metadata`, `ExtractionWarning.details`), los tipos se restringen a estructuras JSON puras mediante un alias recursivo:
  ```python
  JsonValue = Union[None, bool, int, float, str, list["JsonValue"], dict[str, "JsonValue"]]
  ```
  Esto previene la inyección de objetos Python arbitrarios no serializables.
- **Invariantes Estructurales**:
  - `source_page >= 1` y `page_number >= 1` en todos los modelos.
  - En `DocumentIR`: las páginas deben tener `page_number` únicos y orden determinista.
  - En `EstadilloPage`: se valida la consistencia entre `page_number` y el `source_page` de los registros hijos.

### 5. Parseo Conservador de Bloques de Código JSON (`structured.py`)

Los modelos LLM/VLM locales de código abierto frecuentemente devuelven respuestas encerradas en cercas Markdown (```json ... ```) aun cuando se solicita JSON estricto. La estrategia de parseo es conservadora y no realiza extracción laxa en texto libre:
- **Casos válidos admitidos**:
  1. Cadena JSON pura (ej. `{"page_number": 1, ...}`).
  2. Exactamente un único bloque cercado ````json ... ```` o ```` ... ```` con únicamente espacios en blanco antes y después.
- **Casos rechazados con `StructuredOutputParseError`**:
  - Respuestas con texto introductorio o explicativo antes o después del bloque JSON (prosa + JSON).
  - Respuestas con múltiples bloques de código.
  - Comentarios trailing o texto libre posterior.
  - Intentos de extracción parcial por expresiones regulares o búsqueda de llaves en texto libre.
- **Diagnóstico y Redacción**:
  - Las excepciones `StructuredOutputParseError` y `StructuredOutputValidationError` preservan un extracto de `raw_response` acotado (máximo 500 caracteres), sanitizado con `sanitize_message` (eliminando claves API, tokens Bearer y cadenas base64 Data URI) y encadenan la excepción original en `__cause__`.

### 6. Generación Determinista de JSON Schema (`structured.py`)

- `generate_json_schema(schema_class: Type[BaseModel]) -> dict[str, Any]`:
  - Construye el esquema a partir de `schema_class.model_json_schema()` sin mutar la clase Pydantic original.
  - Garantiza `additionalProperties: false` en la raíz y en todas las definiciones anidadas (`$defs`).
  - Soporta tipos `Optional`/null, campos `Path` y modelos genéricos.
  - Estructura el payload para OpenAI/LM Studio:
    ```python
    {
        "type": "json_schema",
        "json_schema": {
            "name": schema_class.__name__,
            "strict": True,
            "schema": schema_dict,
        }
    }
    ```

### 7. Integración en Cliente y Pipeline

- **`LMStudioClient`**:
  - `ask_vision_structured(image_path, prompt, schema, ...)` y `ask_text_structured(prompt, schema, ...)` invocan internamente `ask_vision` y `ask_text` pasando `response_format` generado dinámicamente.
  - No duplican lógica de transporte HTTP, timeouts ni mapeo de excepciones de conexión.
  - Deserializan y validan la respuesta mediante `parse_structured_json(text_response, schema)`.
  - Mantienen intacta y sin cambios la API basada en cadenas (`ask_vision`, `ask_text`, `ask`).
- **`UnlimitedOCRAgent`**:
  - `ask_vision_structured(image_path, prompt, schema, ...)` y `ask_page_vision_structured(page_artifact, prompt, schema, ...)`.
  - Preservan la garantía de aislamiento GPU de PR 3: el worker OCR de Unlimited-OCR finaliza y libera memoria CUDA antes de invocar cualquier consulta estructurada a LM Studio.
